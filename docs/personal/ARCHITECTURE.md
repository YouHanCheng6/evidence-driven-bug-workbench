# 架构与思路链

这里的“思路链”指可公开检查的工程流程、状态转换和证据规则，不包含模型不可观察的内部推理文本。

## 1. 冻结事实

工作流先把工单正文、附件解析结果和页面事实整理成一份规范输入。截图或视频中明确标注的页面事实优先于普通描述；复现前置条件不能在已有视觉事实时反过来主导源码检索。模型后续只接收这一份工单副本，避免不同阶段各自改写事实。

## 2. 确认平台与仓库

客户端确认允许返回有效空结果；此时用工单模块选择仓库，但不凭 Android、iOS、Harmony 等字面词强行认定复现端，因为它们也可能只是对比对象。仓库选择与“实际复现端”是两个不同结论。

## 3. 准备可选上下文

日志和私有业务规则都是可选输入。私有规则由运行环境提供，不进入 Git；它只能补充产品别名、工程别名和模型别名，不能直接成为因果证据。日志中的孤立标识符也不能单独驱动源码定位。

## 4. 获取源码导航候选

Tabby 依据工单、附件、已接受日志锚点和一次受限的概念扩展，在选定源码库中检索小候选集。完整 API/URL 路径可以作为锚点。候选会在不同代码层之间保持平衡，并对与产品目录冲突的结果进行软降权。

## 5. 回到当前 checkout 验证

任何 Tabby 结果在进入模型前，都必须在选定仓库的当前 checkout 中找到完全一致的片段。源码视图只暴露允许的跟踪文件，排除密钥、二进制、依赖和普通构建输出。最终最多向 Codex 提供五个候选窗口；没有真实匹配就传空候选，而不是把“工具可用”包装成证据。

## 6. 一次只读 Codex 调查

每个 Bug 创建一个全新的 Codex 会话。沙箱为只读，审批为拒绝，提示词明确禁止编辑、安装、修复、写工单或声称未执行的测试。Codex 可以继续在源码视图内检索和阅读；只有在它给出精确符号后，才允许用无状态 Tree-sitter 查询辅助定位。

同一个会话负责源码调查和完整报告，不再经过 OpenHands、独立总结器或独立检查模型。这样可以减少事实在多个模型之间转述时的漂移，也让每条结论都回到实际读取的当前源码。

## 7. 校验四段报告

报告必须包含：

1. `一、分析结论`
2. `二、责任端与责任层`
3. `三、根本原因及源码证据`
4. `四、修改范围与其他端风险`

第四节必须以“主要涉及端”开头并包含“本地代码修改”。跨端或后端配合只在证据支持时出现，不能用含糊的“客户端配合”替代责任边界。格式不合格时只在同一会话内进行一次受约束修正，不另起一个会丢失上下文的总结会话。

## 8. 确定性写回与确认

系统从完整报告中投影第三、四节，HTML 转义后通过已认证的工单页面表单提交一次。读回优先检查同一页面，因为历史 API 可能滞后；只有页面无法确认时才回退到历史接口。任何确认路径都不能重复 POST。

## 9. 结束边界

新任务在 `note_written` 后结束，只交付分析、修改范围和处理建议。它不会修改源码、运行修复测试、提交 Git、改变工单状态或自动验收。历史记录中的真实 diff 仍可读取和回滚，但旧执行引擎不能再启动。

## 主助手与批处理

主助手可以查询并保存精确负责人下的 Bug 集合，但保存不等于执行。只有显式运行请求才创建批次；如果该请求本身列出 Bug ID，它覆盖保存集合并保留用户顺序。批次逐条执行、持久化进度，单条失败不会改变其他 Bug 的输入，恢复时也不会重新提交已经确认的备注。

这条链的核心不是增加 Agent 数量，而是缩短信任路径：事实只保存一份，导航不冒充证据，调查只读，外部写入确定且可确认，修改建议与代码执行明确分离。
