# 架构与思路链

这里的“思路链”指可公开检查的工程流程、状态转换和证据规则，不包含模型不可观察的内部推理文本。

## 1. 冻结事实

工作流先把工单正文、附件解析结果和页面事实整理成一份规范输入。截图或视频中明确标注的页面事实优先于普通描述；复现前置条件不能在已有视觉事实时反过来主导源码检索。模型后续只接收这一份工单副本，避免不同阶段各自改写事实。

工单中带标签的测试环境、前置条件、步骤、实际结果、预期结果、复现率与恢复方式只解释一次；未标注内容保持未分类。下游消费这份结构化结果，不能把原正文重新当作另一类事实加入检索。

截图由独立、临时、无工具的 Codex 回合提取，直接启动指定线程，不增加账户路由预检。它只转写可见事实，不决定产品可达性、责任端或根因；公开副本移除了旧的视觉模型实现。示例模型名从 `bug_analysis.visual` 读取，使用者需配置自己可用的模型。正文明确的实际/预期图片归属优先于模型判断，已接受的紧凑视觉事实不会再经历第二次按条数或字符数裁剪。

## 2. 确认平台与仓库

客户端确认允许返回有效空结果；此时用工单模块选择仓库，但不凭 Android、iOS、Harmony 等字面词强行认定复现端，因为它们也可能只是对比对象。明确模块在工单事实支持时拥有仓库族选择权；其他已复现客户端作为跨族观测，不能自动切换源码集合。只有已确认客户端及字面事实全部排除模块族时，才报告真实范围冲突。模块为空或模糊时才由确认客户端决定仓库。仓库选择与“实际复现端”是两个不同结论。

## 3. 准备可选上下文

日志和私有业务规则都是可选输入。私有规则由运行环境提供，不进入 Git；它可辅助产品范围过滤，但不能改写准备会话给出的查询/锚点，更不能直接成为因果证据。

已接受的文本日志（含轮转日志和 ZIP 成员）流式进入私有 SQLite 索引，长物理行分段保存，同时保留来源、行号和段位置。解压安全上限或无法读取的文件会显式诊断，不能把不完整扫描当作没有事件。

一个全新、临时、只读的 Codex 准备回合接收规范工单与截图事实，直接查询日志原文。`search` 的字面/正则结果支持显式分页，`read` / `range` 读取完整物理行及相邻行。沿实际命中的时间、标识与邻近记录寻找新事实，不预设字段或固定检查项，不穷举日志，也不采用固定保留条数。没有附件或没有可接受日志时创建有效空索引，不因此中止源码调查。旧 `symbols` 字段发现、关键词表、停用词、中文拆词和业务词到代码词映射已移除。

准备会话交付关键日志的来源/行号，并同时给出直接供 Tabby 使用的自然语言 `query` 和最多 8 个逐字摘自工单、截图或实际已读日志的 `anchors`。截图背景只有与工单行为直接相关时才能进入检索；不得猜文件名、翻译造词或另写根因总结。后端恢复完整、脱敏的原始记录，去重后提供给最终调查，同时私有保存命令及分页/返回引用轨迹。模型改写的摘要不替代原始记录，旧信号打分、摘录截断和事务合并路径已移除。空结果不证明事件不存在；原始记录只证明它实际记录的事实。公开仓库只有代码，没有日志、索引、真实查询或轨迹。

## 4. 获取源码导航候选

Tabby 通过自身的 BM25、向量和 RRF 混合检索获取小候选集，直接使用准备会话的语义查询作为主通道；只有向量命中、BM25 为零的结果也可以进入候选。精确 grep 仅消费准备会话给出的原文锚点，作为精度补充与可用性回退。后端不从票据、模块、别名或日志重新生成另一套查询，也不补造资源键、代码职责词或概念回退词。

语义通道保留 Tabby 排名，精确通道在有界候选池内排序，再按文件统一融合；不混用原始分数，重复片段不挤占名额。grep 文件先跨锚点去重再应用共享候选上限，小候选向量重排只辅助精确通道。原生实现层保持同级候选资格；私有 Tabby 配置支持 ArkTS、Objective-C 和 Swift，`.ets` 被标为 Harmony 原生源码。

产品配置只限定可达源码范围，不生成候选、不扩展 Tabby 查询、不给某个文件预留名额。产品族仅在所有匹配配置的模块、具体页面覆盖和运行配置一致时才能确定；示例字段 `examplePageConfig.data` 只有解析到当前源码组件的字符串才算页面覆盖，功能开关或数值参数不能制造虚假的产品分歧。已确定产品配置会过滤其他产品独占实现，但共享或静态未决路径仍保留资格。

## 5. 回到当前 checkout 验证

任何 Tabby 结果在进入模型前，都必须在选定仓库的当前 checkout 中找到完全一致的片段。源码视图只暴露允许的跟踪文件，排除密钥、二进制、普通依赖和生成输出；已跟踪且包入口实际指向其中的 vendored 运行时目录是受限例外。最终最多向 Codex 提供五个候选窗口；没有真实匹配就传空候选。

Git 历史限定在已验证故障入口文件，一次读取最多 8 条近期变更。允许条件是明确回归/版本问题、已知直接变更能够关闭决策，或准备以“当前代码已修复/无需重复修改”收尾。最后一种情况必须取得与异常直接相关的修复日期：若超过一个月且最新代码仍能复现，该处理是长期既有行为，应继续找下一故障点或明确证据缺口，不能用“可能未发布”结束。提交日期/标题元数据与截断 diff 分开处理，正文截断不等于没有日期。未知构建身份本身不授权查历史，也不能替代上述日期核验；对照、见证、风险和相似页面不查历史。

## 6. 一次只读 Codex 调查

每个 Bug 创建一个全新的 Codex 会话。沙箱为只读，审批为拒绝，提示词明确禁止编辑、安装、修复、写工单或声称未执行的测试。Codex 可以继续在源码视图内检索和阅读；只有在它给出精确符号后，才允许用无状态 Tree-sitter 查询辅助定位。

材料先分为故障目标、正确对照、现象见证、风险候选和无关候选。只对故障目标核对四项：真实入口、失败机制、现象形成、责任与修改/外部输入边界。每次读取必须能改变一项仍开放的决策，形成互证闭环后停止；没有固定调用次数，也不会为了填满报告栏目继续搜索。

可选 `examplewiki` 只在工单、源码和同事务证据已形成嵌入式故障假设后查询。仅把嵌入式契约与日志专家或其他输入实际交付的观测比较，不把空日志结果解释为没有事件。符合契约则排除嵌入式责任并停止；仍有冲突才追同一命令、事件或错误的产生条件及必要传递边。转发、枚举、定义或源码覆盖缺口都不是产生方证据。只有八个示例只读工具获准免交互调用；凭据通过运行环境传入，不进入提示词。公开代码不包含服务实现或知识内容。只读沙箱限制写入，但并不提供整台主机的读取隔离，实际部署仍需隔离文件权限与工具权限。

同一个会话负责源码调查和完整报告，不再经过 OpenHands、独立总结器或独立检查模型。这里的“单会话”专指最终调查；此前的视觉提取和可选日志专家各有受限回合，后续可选修改执行也不继承调查权限。这样可以减少根因结论在多个模型之间转述时的漂移，也让每条结论都回到实际读取的当前源码。

## 7. 校验四段报告

报告必须包含：

1. `一、分析结论`
2. `二、责任端与责任层`
3. `三、根本原因及源码证据`
4. `四、修改范围与其他端风险`

第四节必须以“主要涉及端”开头，并在“本地代码修改”之前固定给出“待确认输入：”；无缺口则明确写“无”，有缺口则写明提供方、精确信息和到位后的修改动作。需要修改时，在“本地代码修改”之后重复列出完整仓库限定路径；无需修改时只写“本地代码修改：无”，其后不再列源码路径，避免误启动执行器。跨端或后端配合只在证据支持时出现，不能用含糊的“客户端配合”替代责任边界。格式不合格时只在同一会话内进行一次受约束修正，不另起一个会丢失上下文的总结会话。

使用 WIKI 后第二节必须明确写“嵌入式判定”。已排除或未涉及的责任不能重新出现在第四节主责、配合或待确认输入中；缺失资料归其实际提供方。远端引用与当前本地源码引用分别标明。

## 8. 确定性写回与确认

系统从完整报告中投影第三、四节，HTML 转义后通过已认证的工单页面表单提交一次。读回优先检查同一页面，因为历史 API 可能滞后；只有页面无法确认时才回退到历史接口。任何确认路径都不能重复 POST。

## 9. 可选的有界修改执行

公开示例默认关闭 `bug_analysis.repair.enabled`，此时备注确认后以 `note_written` 结束。部署方显式启用后，工作流先进入 `repairing`，由所配置的 Gateway 模型执行**本次 `analysis_report` 第四节**中的明确本地修改；历史复用备注既不能提供修改指令，也不能压制本次新报告的修改要求。

执行器先登记完整本地要求清单，逐项保留原文、文件和结果。正文要求是任务单位，围栏中的修改前/后代码只是实现示例，不另拆为重复任务。它只能读取第四节引用文件，只能在本地修改段列出的文件上暂存精确替换；修改前必须读取，新增文件必须被报告明确要求。待确认输入、条件建议、外部配合与已满足要求不强行修改。清单不能删项，单次模型运行成功也不等于所有要求完成。正常回复后仍缺有效清单或存在待处理项时，最多进行一次受限补全，沿用原清单；中断不会因此被视为完成。

后端在模型结束和并发变更检查通过后统一落盘，按实际文件与逐项结果生成 `completed`、`partial`、`incomplete` 或 `not_required`。未完成项必须给出原因；部分成功保留已完成修改，串行批次继续其他 Bug。执行器没有 shell、测试、Git 提交、MCP 或重新调查能力，不自动改变工单状态或验收。正常执行处理结束时，保存结果及实际文件清单后才进入 `note_written`；这个终态表示流程结束，不代表修复全部完成。运行或落盘异常仍记为 `failed`，保留分析、已确认备注和实际修改状态。

## 10. 快照回退与恢复

工作台按钮与 IM 的 `回退 #<Bug ID>` / `恢复 #<Bug ID>` 共享所有者范围内的前后快照 API。按 Bug 操作选择该用户最新的实际修改，跳过较新的零修改分析；不新建调查、不重新运行模型。前后内容只保存在私有运行数据里，HTTP 状态投影不返回源码内容。

内容冲突会保留后续编辑，多文件操作失败会撤销本次操作已经写入的部分。已有历史真实 diff 仍可读取；只有具备必要前后内容的记录才能双向回退/恢复，缺失后版本的旧记录不能声称可恢复。历史执行引擎不能重新启动。

## 11. 操作者本机交付

`bug_git_delivery.py` 是独立的确定性 Git 边界。若显式启用 `bug_analysis.git_relay`，实际修复先经临时 Git 索引形成仅含本 Bug 文件的中转提交，只推送到配置的私有中转库，不移动修复 checkout 的 HEAD/索引、不写其正式上游。公开示例默认关闭此能力，远端地址为空，作者身份使用示例值。

操作者明确请求 `拉取 #<Bug ID>` 后，系统按正式远端身份定位匹配的个人 checkout，在当前分支应用中转补丁，保持未提交，不新建或切换分支；补丁冲突则拒绝写入。明确批准 `提交拉取并推送 #<Bug ID>` 后，才在同一 checkout/分支提交原修复文件集的完整当前内容——包含这些文件内后续手工修改，其他文件排除——再对已有跟踪分支执行 rebase 和 push。部署者必须自行完成测试；交付记录不证明测试通过。

回退/恢复仍作用于修复 checkout 和中转分支，不回写已经拉取的个人 checkout；正式提交后的状态单独呈现。飞书本机拉取/提交另要求 `channels.feishu.bug_workbench_server_local_open_id` 精确匹配配置的操作者，空值拒绝执行。这个配置在公开版仅是授权白名单，不是设备配对。按作者要求，本版不含同事执行器、设备凭据、远端队列或专用服务接口。

## 主助手与批处理

查询/选择适配与执行分开，保存集合不等于执行。显式批次请求列出 Bug ID 时，覆盖保存集合并保留用户顺序；飞书明确要求分析所列编号时可以直接进入串行批次。批次按当前消息/工具调用标识去重，同一提供方消息重投或同次工具重试才复用，新消息即使重复相同编号也创建新批次。启动回复立即返回批次 ID、有效 ID 和顺序，后台继续；用户停止时持久化取消当前与排队项。单条失败不会改变其他 Bug 的输入，恢复时也不会重新提交已经确认的备注。低层单 Bug 启动与批次适配均保留，模型实际获得哪些工具以装配代码为准，不能只凭存在某个工具文件就认定已暴露。

飞书控制消息先经过窄文本门控，只有可能涉及取消、回退、恢复、拉取或提交的消息才进入无工具意图模型。完整操作转为确定性内部命令，缺 Bug 编号时询问，不从历史猜测；其他消息保留原分析、查询或聊天路径。公开版没有“绑定本机”操作。

前端不再对产品目标进行人工确认；唯一保留的预分析确认是“视频是唯一有效附件”时，用户选择分析或跳过。定时日报另可选把已分类行按 Bug ID 投影到飞书多维表格；看板写入失败不会否定已生成的文本报告。

这条链的核心是缩短信任路径：事实只保存一份，导航不冒充证据，调查只读，外部写入确定且可确认，修改建议与代码执行权限明确分离，实际修改可核对且有冲突保护。
