# 架构与思路链

这里的“思路链”指可公开检查的工程流程、状态转换和证据规则，不包含模型不可观察的内部推理文本。

## 1. 冻结事实

工作流先把工单正文、附件解析结果和页面事实整理成一份规范输入。截图或视频中明确标注的页面事实优先于普通描述；复现前置条件不能在已有视觉事实时反过来主导源码检索。模型后续只接收这一份工单副本，避免不同阶段各自改写事实。

截图由独立、临时、无工具的 Codex 回合提取。它只转写可见事实，不决定产品可达性、责任端或根因；这次公开副本移除了旧的视觉模型实现。示例模型名从 `bug_analysis.visual` 读取，使用者需配置自己可用的模型。

## 2. 确认平台与仓库

客户端确认允许返回有效空结果；此时用工单模块选择仓库，但不凭 Android、iOS、Harmony 等字面词强行认定复现端，因为它们也可能只是对比对象。仓库选择与“实际复现端”是两个不同结论。

## 3. 准备可选上下文

日志和私有业务规则都是可选输入。私有规则由运行环境提供，不进入 Git；它只能补充产品别名、工程别名和模型别名，不能直接成为因果证据。日志中的孤立标识符也不能单独驱动源码定位。

已接受的文本日志（含压缩包成员）分块扫描进入私有只读索引，避免只读取文件前部而丢掉后续事件。解压安全上限会显式诊断。模型只接收有界摘录，按字段和可选精确事件时间查询；有界完整成员 ID 集合与不完整集合分别标注，未核验集合不能变成已证事实。仓库只保留索引代码，没有索引数据。

## 4. 获取源码导航候选

Tabby 通过自身的 BM25、向量和 RRF 混合检索获取小候选集，分别接收字面证据和简短的代码职责描述。架构候选、精确检索和概念检索保留各自排序，再按文件统一融合；重复片段不能挤占候选名额，不混用各通道原始分数。产品族仅在所有匹配配置的模块、页面覆盖和运行配置一致时才能确定。示例页面覆盖字段 `examplePageConfig.data` 优先指向实际页面；路由、相邻页面转换和资源值补充导航。候选在可能的原生与 RN 实现层之间保持覆盖，但这些线索均须回到当前源码验证。

## 5. 回到当前 checkout 验证

任何 Tabby 结果在进入模型前，都必须在选定仓库的当前 checkout 中找到完全一致的片段。源码视图只暴露允许的跟踪文件，排除密钥、二进制、依赖和普通构建输出。最终最多向 Codex 提供五个候选窗口；没有真实匹配就传空候选。Git 历史仅在明确回归/版本问题，或已知旧值到当前值的直接变更能关闭决策时，对已验证故障入口查询一次；当前无法复现、构建版本未知均不能单独授权查历史。正确对照、现象见证和相似页面不查历史。

## 6. 一次只读 Codex 调查

每个 Bug 创建一个全新的 Codex 会话。沙箱为只读，审批为拒绝，提示词明确禁止编辑、安装、修复、写工单或声称未执行的测试。Codex 可以继续在源码视图内检索和阅读；只有在它给出精确符号后，才允许用无状态 Tree-sitter 查询辅助定位。

材料先分为故障目标、正确对照、现象见证、风险候选和无关候选。只对故障目标核对四项：真实入口、失败机制、现象形成、责任与修改/外部输入边界。每次读取必须能改变一项仍开放的决策，形成互证闭环后停止；没有固定调用次数，也不会为了填满报告栏目继续搜索。

可选 `examplewiki` 只在工单、源码和同事务证据已形成嵌入式故障假设后查询。先核对契约与观测：符合契约则排除嵌入式责任并停止；仍有冲突才追同一命令、事件或错误的产生条件及必要传递边。只有八个示例只读工具获准免交互调用；凭据通过运行环境传入，不进入提示词。公开代码不包含服务实现或知识内容。只读沙箱限制写入，但并不提供整台主机的读取隔离，实际部署仍需隔离文件权限与工具权限。

同一个会话负责源码调查和完整报告，不再经过 OpenHands、独立总结器或独立检查模型。这样可以减少事实在多个模型之间转述时的漂移，也让每条结论都回到实际读取的当前源码。

## 7. 校验四段报告

报告必须包含：

1. `一、分析结论`
2. `二、责任端与责任层`
3. `三、根本原因及源码证据`
4. `四、修改范围与其他端风险`

第四节必须以“主要涉及端”开头，并在“本地代码修改”之前固定给出“待确认输入：”；无缺口则明确写“无”，有缺口则写明提供方、精确信息和到位后的修改动作。跨端或后端配合只在证据支持时出现，不能用含糊的“客户端配合”替代责任边界。格式不合格时只在同一会话内进行一次受约束修正，不另起一个会丢失上下文的总结会话。

使用 WIKI 后第二节必须明确写“嵌入式判定”。已排除或未涉及的责任不能重新出现在第四节主责、配合或待确认输入中；缺失资料归其实际提供方。远端引用与当前本地源码引用分别标明。

## 8. 确定性写回与确认

系统从完整报告中投影第三、四节，HTML 转义后通过已认证的工单页面表单提交一次。读回优先检查同一页面，因为历史 API 可能滞后；只有页面无法确认时才回退到历史接口。任何确认路径都不能重复 POST。

## 9. 结束边界

新任务在 `note_written` 后结束，只交付分析、修改范围和处理建议。它不会修改源码、运行修复测试、提交 Git、改变工单状态或自动验收。历史记录中的真实 diff 仍可读取和回滚，但旧执行引擎不能再启动。

## 主助手与批处理

主助手可以查询并保存精确负责人下的 Bug 集合，但保存不等于执行。只有显式运行请求才创建持久化后台批次；如果该请求本身列出 Bug ID，它覆盖保存集合并保留用户顺序。启动回复立即返回批次 ID、有效 ID 和顺序，后台继续串行执行；用户停止时持久化取消当前与排队项。单条失败不会改变其他 Bug 的输入，恢复时也不会重新提交已经确认的备注。

前端不再对产品目标进行人工确认；唯一保留的预分析确认是“视频是唯一有效附件”时，用户选择分析或跳过。定时日报另可选把已分类行按 Bug ID 投影到飞书多维表格；看板写入失败不会否定已生成的文本报告。

这条链的核心不是增加 Agent 数量，而是缩短信任路径：事实只保存一份，导航不冒充证据，调查只读，外部写入确定且可确认，修改建议与代码执行明确分离。
