# 失败模式、恢复与幂等

| 失败点 | 行为 | 不允许的行为 |
| --- | --- | --- |
| 附件无法解析 | 保留工单文本和明确缺口，必要时终止 | 猜测截图或视频内容 |
| 平台结果为空 | 使用模块做仓库回退，但不虚构复现端 | 用关键词强行覆盖语义结果 |
| 没有附件或可接受日志 | 创建有效空索引，准备会话仍使用工单和截图 | 因零日志阻断源码调查，或把无输入当作无事件 |
| 私有规则不可用 | 以空的可选上下文继续 | 把工具不可用解释成业务结论 |
| 日志扫描不完整或分页查询为空 | 保存扫描诊断及分页信息；仅引用实际返回的完整记录 | 用空结果证明事件不存在，或把半条记录当作完整证据 |
| Tabby 不可用或无命中 | 使用准备会话原文锚点进行有界精确 grep；仍无匹配则传空候选 | 重新造词、概念扩展或把搜索服务就绪当成证据 |
| 候选与 checkout 不一致 | 丢弃候选并记录原因 | 引用索引中的过期片段 |
| 准备判定当前代码已修复 | 查已验证入口的最多 8 条文件变更，核对直接相关修复日期与当前异常路径 | 超过一个月且仍复现时以“可能未发布”结束，或从相似代码补造当前根因 |
| 可选 WIKI 不可用 | 保留实际缺口与提供方；同一开放故障假设下 HTTP 5xx 仅允许收窄一次 | 将覆盖不足认定为嵌入式责任 |
| WIKI 已排除嵌入式责任 | 停止该侧调查，报告保持责任一致 | 再次要求嵌入式配合或提供无关输入 |
| Codex 认证/运行时缺失 | 在调查前失败，保留已准备事实 | 回退到未声明的模型或旧引擎 |
| Codex 超时/空响应 | 保存错误和已有状态，允许显式重试 | 伪造报告或悄悄启动第二套流程 |
| 报告格式不合格 | 同一会话最多一次受约束修正 | 新开总结会话丢失证据来源 |
| 备注提交失败 | 保持未确认状态，交由恢复逻辑判断 | 在结果不明时盲目重复 POST |
| 页面读回滞后 | 页面优先，必要时查询历史接口 | 因切换确认渠道再次提交 |
| 修改未启用 | 备注确认后结束，交付完整分析与建议 | 暗中回退到其他执行器 |
| 修改存在待确认输入 | 明确阻碍，只执行其他无条件的本地要求 | 把条件建议改写成立即执行指令 |
| 围栏示例被登记为独立要求 | 拒绝重复清单项，以正文要求为准 | 将修改前/后示例拆成多份任务 |
| 正常执行回复仍缺清单或留有 pending | 最多一次受限补全，沿用原清单后如实分类 | 删除难项、无限续跑或把中断当完成 |
| 部分修改未完成 | 保留成功修改，逐项说明原因并报告 partial/incomplete，批次继续 | 用模型回合成功或终态冒充全部完成 |
| 修改前源码已变化或文件不在范围内 | 阻止相应写入并保留用户修改 | 覆盖脏文件、扩大修改范围或重新调查 |
| 修改运行或统一落盘失败 | 记录 failed，保留分析、已确认备注与实际修改/快照状态 | 把执行故障伪装成 note_written 或抹去已经发生的修改 |
| 回退/恢复遇到内容冲突 | 保留当前文件并返回冲突 | 覆盖后续编辑，或调用模型重做一份修改 |
| 旧快照缺少修改后内容 | 保留历史结果并标明无法恢复 | 仅凭 diff 或文字报告声称可恢复 |
| 中转配置未启用或发布失败 | 保留本地修复，报告交付未完成 | 自动改写正式上游或覆盖已有其他中转提交 |
| 本机拉取补丁冲突 | 拒绝应用，保持当前分支和用户文件 | 留下半份补丁、新建分支或擅自提交 |
| 飞书本机操作者未配置/不匹配 | 拒绝本机拉取与提交 | 把其他发送者请求回退到服务器 Git 或同事队列 |
| 正式提交后 rebase 冲突或 push 失败 | 保留真实提交/冲突状态，返回相应结果供显式恢复 | 宣称已推送、覆盖远端或重新创建一份修复 |
| 批次中单条失败 | 记录该项并继续/恢复其余项 | 改写冻结的 ID 顺序或重复已完成项 |
| 用户停止批次 | 持久化取消当前与排队项，中断当前调查 | 进程重启后自动续跑已取消项 |
| 看板同步失败 | 保留完整文本日报并报告看板错误 | 因外部看板失败否定工单快照 |

## 单次写入原则

写回前先从完整报告确定性提取第三、四节，再在传输边界做 HTML 转义。POST 只发生一次；提交后的页面和历史接口都是确认渠道，不是第二次写入入口。即使读回暂时不可见，也必须先分辨“提交失败”和“提交成功但读取滞后”。

## 恢复边界

持久状态记录已完成阶段，使进程重启后可以从安全边界继续。已经确认的备注不会在恢复时重写；批次保存当前索引和每项结果。可选修改只在新结果契约、明确启用且尚未尝试时进入，不能借备注重试给旧记录追加执行能力。

启用修改时 `repairing` 仍是忙碌状态，保存逐项结果和实际文件后才以 `note_written` 结束。`repair_outcome` 独立表达全部完成、部分完成、未完成或无需修改；部分成功不是失败回滚指令，也不要求串行批次停下等待新的批准。执行器不提供测试、命令、提交或工单状态变更。

回退/恢复在写源码前保存前后内容和待执行动作，重复请求可继续该动作而不重复写入。每工作流锁串行化状态变更，共享源码写锁覆盖修改执行与快照操作；多文件写入失败会撤销该次操作已经写入的部分。按 Bug 操作只选择所有者最新的实际修改记录，较新零修改分析不会遮蔽它。

批次幂等限于同一个当前请求：同一消息重投/工具重试复用，新消息重复相同 Bug ID 仍是新批次。交付是另一条明确授权边界：中转不移动修复 checkout 的 HEAD/索引，本机拉取保持未提交；正式提交包含原修复文件集的完整当前内容（包括这些文件内的后续手工修改），不包含其他文件。回退/恢复只作用于修复 checkout 与中转分支，不撤销已拉取的个人 checkout。没有同事设备配对和远端执行恢复路径。

## 历史兼容

旧记录可能含真实 diff、验收和回滚信息。系统保留展示与具备完整快照时的回退/恢复能力，但不会把历史字段解释为旧引擎仍可启动。新修改执行器复用快照协议，不进入旧验收/修复选择流程。公开副本中的相关兼容代码应与新任务可达路径分开阅读；真实 diff 与前后源码内容属于运行数据，均不进入本仓库。
