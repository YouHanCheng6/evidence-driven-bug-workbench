# 提示词与输出约束

提示词的目标不是要求模型“想得更多”，而是把事实、权限、证据标准和交付格式写成可校验契约。

## 输入分区

Codex 调查包按来源分开：规范工单、附件/页面事实、平台与仓库结论、可选日志原始记录、可选业务别名、经当前 checkout 复核的源码候选。工单正文的语义角色只解释一次，后续不能重新引入原正文改变角色。每段都标记证据等级，避免把检索命中、日志猜测或业务常识混成已证明根因。

日志专家的契约独立于最终调查：只读查询，分别检查工单具体事实；字段发现只用于找到真实名称，再回到完整原始行。它仅返回来源与物理行号，由后端恢复脱敏记录，不能把生成摘要当成记录。一个事实已有充分记录时检查其余事实，没有固定记录数，也不能为了补满数量穷举。最终调查只比较实际收到的运行观测，空结果不证明事件不存在。

## 权限边界

系统提示明确规定：

- 读取选定源码视图，并仅在满足证据条件时访问已配置的示例 WIKI 只读接口；
- 不编辑文件、不安装依赖、不提交 Git；
- 不直接访问或写入工单系统；
- 不把 Tabby 候选、工具就绪或文件名当成证据；
- 不声称运行过未实际运行的测试；
- 证据不足时明确写出未知项和最小补证动作。

运行时使用只读沙箱与拒绝审批；可选 WIKI 的八个示例工具单独列入免交互只读白名单。该沙箱不等于主机级读取隔离，部署方仍需限制可见文件与 MCP 权限。

## 调查策略

提示词要求从用户可见现象寻找最近失败边界，沿真实调用关系阅读源码，并区分：

- 票据明确要求是否满足；
- 静态源码机制是否成立；
- 运行时触发是否被日志或附件证明；
- 修改范围和跨端风险是否有证据。

候选片段只是起点。Codex 可以在源码视图内继续搜索；若候选全部无关，也必须舍弃，而不能为了填满报告强行引用。

材料先分为故障目标、正确对照、现象见证、风险候选和无关候选。仅故障目标需要入口、机制、现象与责任/方案四项闭环。下一次读取不能改变开放决策时立即停止；批量检索精确锚点并合并相邻窗口，辅助工具失败不反复重试。

Git 历史仅针对明确回归/版本问题，或已知直接变更能关闭决策时的已验证故障入口。当前未复现和未知构建身份均不能单独授权查历史；对照、见证、风险和相似页面禁止查历史。即使命中历史移除，也必须先证明票据异常触发在当前产品确实到达接收/调用条件与预期动作，才能认定当前检出版已修复；存在函数、回调或事件本身不构成闭环，更不能证明截图对应版本。

示例 WIKI 必须由已有嵌入式故障证据触发，单独的设备数据、错误码、未知固件或系统间差异不足以触发。调用前说明待改变的责任决策；契约与同事务观测一致则停止。使用后输出明确嵌入式判定，已排除的责任不能再被要求配合。

涉及共享代码或原生契约的修改，只沿拟议变更直接涉及的注册、调用、回调和清理逻辑检查平台兼容性；必要作用域保护写进原修改方案，不扩展成全仓或全平台审计。

## 四段式报告

最终回答严格使用四个一级标题：

1. `一、分析结论`：直接回答问题、确定性和关键未知项。
2. `二、责任端与责任层`：区分复现端、责任仓库和具体代码层。
3. `三、根本原因及源码证据`：给出路径、符号/行段、机制和从现象到失败边界的链路。
4. `四、修改范围与其他端风险`：以“主要涉及端”开头；在“本地代码修改”前必须有“待确认输入：”，无缺口写“无”，有缺口则标明提供方、精确输入和后续动作；再列出最小修改面、验证面和有证据的跨端影响。

第三、四节是写回工单的确定性投影；第一、二节留在完整调查记录中。报告不能输出模型的隐藏思维过程，只输出可复核结论、证据和工程建议。

## 修改执行契约

这是备注确认后、配置明确启用才可进入的独立阶段，公开示例默认关闭。输入是本次 `analysis_report` 第四节，不能用复用的历史工单备注替代。执行器不重新调查，也不运行测试、命令或提交。

`track_repairs` 先登记全部本地修改要求，每项保留原文与对应文件；同一文件的不同要求分别跟踪。后续不能删改要求，`replace_source` 必须关联已登记的项，并先读取当前文件。只有明确且无待确认条件的本地修改才能执行；外部配合、条件建议、已满足项和无需修改项分别说明原因。

逐项结果使用 `applied`、`already_satisfied`、`blocked`、`not_required`，待处理项不能冒充完成。`applied` 必须有对应暂存改动及实际落盘文件支持，最终汇总还要区分全部、部分、未完成或无需修改。模型的“已完成”文字不替代后端清单与文件校验。

## 修正策略

解析器先检查标题顺序、必需措辞和空节。若只是格式不合格，在同一会话内发送一次短修正要求，保留已经调查过的上下文；若内容缺少源码证据，则失败或降级说明，不能让另一个总结模型凭空补证。

具体调查提示词与校验逻辑在 `backend/app/gateway/bug_codex_summary.py`，日志选择契约在 `bug_log_expert.py`，修改建议约束在 `bug_change_advice.py`，独立修改执行契约在 `bug_note_repair.py`。
