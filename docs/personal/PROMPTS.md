# 提示词与输出约束

提示词的目标不是要求模型“想得更多”，而是把事实、权限、证据标准和交付格式写成可校验契约。

## 输入分区

Codex 调查包按来源分开：规范工单、附件/页面事实、平台与仓库结论、可选日志、可选业务别名、经当前 checkout 复核的源码候选。每段都标记证据等级，避免把检索命中、日志猜测或业务常识混成已证明根因。

## 权限边界

系统提示明确规定：

- 只能读取选定源码视图；
- 不编辑文件、不安装依赖、不提交 Git；
- 不直接访问或写入工单系统；
- 不把 Tabby 候选、工具就绪或文件名当成证据；
- 不声称运行过未实际运行的测试；
- 证据不足时明确写出未知项和最小补证动作。

这些文字约束之外，运行时同时使用只读沙箱与拒绝审批，避免安全只依赖模型自律。

## 调查策略

提示词要求从用户可见现象寻找最近失败边界，沿真实调用关系阅读源码，并区分：

- 票据明确要求是否满足；
- 静态源码机制是否成立；
- 运行时触发是否被日志或附件证明；
- 修改范围和跨端风险是否有证据。

候选片段只是起点。Codex 可以在源码视图内继续搜索；若候选全部无关，也必须舍弃，而不能为了填满报告强行引用。

## 四段式报告

最终回答严格使用四个一级标题：

1. `一、分析结论`：直接回答问题、确定性和关键未知项。
2. `二、责任端与责任层`：区分复现端、责任仓库和具体代码层。
3. `三、根本原因及源码证据`：给出路径、符号/行段、机制和从现象到失败边界的链路。
4. `四、修改范围与其他端风险`：以“主要涉及端”开头，包含“本地代码修改”，列出最小修改面、验证面和有证据的跨端影响。

第三、四节是写回工单的确定性投影；第一、二节留在完整调查记录中。报告不能输出模型的隐藏思维过程，只输出可复核结论、证据和工程建议。

## 修正策略

解析器先检查标题顺序、必需措辞和空节。若只是格式不合格，在同一会话内发送一次短修正要求，保留已经调查过的上下文；若内容缺少源码证据，则失败或降级说明，不能让另一个总结模型凭空补证。

具体提示词模板与校验逻辑在 `backend/app/gateway/bug_codex_summary.py`，修改建议约束在 `bug_change_advice.py`。
